## Слайд 2. Актуальность и цель

Объектом работы является процесс цифровой поддержки настольной ролевой системы E'Magios Core.

Предметом является веб-платформа для хранения, поиска и использования правил, справочников и пользовательских персонажей.

Актуальность проекта связана с тем, что настольные ролевые системы содержат большой объём информации: правила, заклинания, эффекты, игровые сущности и данные персонажей. Если такая информация хранится в разрозненных документах, пользователю сложно быстро находить нужные материалы и сопровождать игровой процесс.

Разработанная веб-платформа решает эту проблему за счёт структурированного справочника, интерактивной базы данных, редактора персонажей и облачного доступа с разных устройств.

Новизна работы заключается в объединении материалов собственной настольной ролевой системы, интерактивной базы данных, облачного хранения и редактора персонажей в единой веб-платформе. В проекте используется не просто набор статических страниц, а архитектура с React-приложением, Firestore как основным источником данных, клиентским кешированием и автоматизированным переносом контента из Obsidian.

## Слайд 3. Актуальность и цель

Настольная ролевая игра, или НРИ, - это формат игры, в котором участники совместно создают историю, а правила системы описывают персонажей, проверки, боевые ситуации, магию и развитие сюжета. В отличие от компьютерной игры, большая часть игрового процесса происходит через общение игроков, мастера и работу с правилами.

Сейчас НРИ становятся всё популярнее, в том числе в СНГ. Это видно по активности сообществ, тематическим сайтам, каналам, сервисам для ведения игр и количеству материалов, посвящённых настольным ролевым системам. На слайде приведены примеры таких ресурсов и визуальных материалов, показывающих интерес аудитории к цифровым инструментам для НРИ.

E'Magios Core - это авторская настольная ролевая система о магах, школах магии, создании заклинаний и развитии персонажей. Для такой системы нужен не только текст правил, но и удобный цифровой инструмент: справочник, поиск, фильтрация, редактор персонажей и хранение пользовательских данных.

## Слайд 7. Инструментальные средства

На этом слайде показаны инструменты, которые использовались при разработке проекта.

React выбран для реализации интерактивного интерфейса: базы данных, фильтров, модальных окон, профиля и редактора персонажей. Эти части требуют управления состоянием и переиспользуемых компонентов, поэтому компонентный подход React хорошо подходит для проекта.

TypeScript используется для типизации сущностей: заклинаний, школ, новостей, персонажей и репозиториев. Это помогает заранее находить ошибки в структуре данных и делает код надёжнее.

Vite используется как инструмент сборки и локальной разработки. Он быстро запускает dev server и собирает production-версию React-приложения.

Firebase выбран как backend-платформа: Authentication отвечает за вход через Google, Cloud Firestore хранит справочник, новости, профили и персонажей, а Security Rules ограничивают доступ к данным.

Obsidian Vault используется как источник исходного контента, потому что материалы системы изначально ведутся в Markdown. Python-скрипты преобразуют эти материалы в JSON, после чего данные импортируются в Firestore. Для разработки также использовались Git, npm, IndexedDB, Visual Studio Code и Cursor.

## Слайд 8. Архитектура

На слайде показан общий поток данных проекта.

Контент создаётся в Obsidian Vault, затем Python-скрипты преобразуют Markdown в JSON. После этого import scripts загружают данные в Cloud Firestore.

Во время работы сайта Firestore является основным источником данных. React-приложение не обращается к нему напрямую из компонентов, а использует Repository Layer. Это позволяет централизованно управлять загрузкой, кешированием и обработкой ошибок.

Для ускорения повторной загрузки справочника используется IndexedDB cache. Пользователь взаимодействует только с React UI, а авторизация выполняется через Firebase Authentication.

## Слайд 9. База данных

На слайде представлена логическая модель данных Cloud Firestore.

В базе данных выделены несколько групп коллекций. Первая группа - служебные документы, например contentManifest. Он хранит версии опубликованных коллекций и используется для понимания актуальности клиентского кеша.

Вторая группа - публичный справочник: заклинания, школы магии, эффекты, действия, навыки, архетипы, рецепты и другие игровые сущности. Эти данные доступны для чтения только в опубликованном состоянии, а запись с клиента запрещена.

Третья группа - пользовательские данные. Документ users/{uid} хранит профиль пользователя, а подколлекция users/{uid}/characters хранит его персонажей. Доступ к этим данным разрешён только владельцу соответствующего uid.

Так как используется NoSQL Firestore, связи между персонажами и справочником являются логическими ссылками по id или названию, а не SQL foreign key. Разрешение таких связей выполняется на уровне приложения.

## Слайд 14. Тестирование и результаты

В ходе разработки была проведена ручная проверка ключевых пользовательских сценариев: навигации, работы базы данных, поиска, фильтрации, авторизации, профиля и редактора персонажей.

По результатам проверки были приняты несколько оптимизационных решений.

Во-первых, был выделен единый Repository Layer для доступа к Firestore, чтобы UI-компоненты не зависели напрямую от Firebase SDK.

Во-вторых, runtime JSON fallback был удалён, чтобы не возникало рассинхронизации между Firestore и статическими файлами.

В-третьих, для справочника используется IndexedDB cache, который ускоряет повторную загрузку последней успешно полученной версии данных.
