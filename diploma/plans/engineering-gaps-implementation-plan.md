# План закрытия инженерных gap'ов проекта

## Назначение документа

Документ описывает, что необходимо добавить в проект E'Magios Core в первую очередь для достижения уровня production-ready разработки:

- CI/CD workflow;
- quality gate (lint, format, typecheck, tests);
- процесс публикации контента `draft -> review -> publish`;
- корректное версионирование контента;
- наблюдаемость (ошибки, производительность, метрики публикации);
- единый README с архитектурой и roadmap миграции.

## Снимок текущего состояния (актуально для этого репозитория)

Что уже есть:

- `apps/web` на React + TypeScript + Vite;
- `scripts/import-content` для загрузки контента;
- `firestore.rules` и `firestore.indexes.json`.

Что отсутствует на момент ревизии:

- `.github/workflows` (CI и deploy еще не заведены);
- `scripts/data-processing` (pipeline нормализации/валидации пока не выделен в отдельный контур);
- quality-команды в `apps/web` (`lint`, `format:check`, `typecheck`, `test`, `check`).

Из этого следует, что первым шагом нужно закрыть базовый quality gate и CI, а затем разворачивать процессы публикации и наблюдаемости.

## 1. CI/CD workflow в `.github/workflows`

## Цель

Автоматизировать проверку качества, сборку и публикацию проекта, исключить ручные ошибки перед деплоем.

## Что добавить

Минимум два workflow:

1. `ci.yml` (запуск на `pull_request` и `push` в `dev/main`):
   - установка зависимостей;
   - `lint`;
   - `format:check`;
   - `typecheck`;
   - тесты;
   - build;
   - проверка артефактов.

2. `deploy.yml` (запуск после успешного CI на `main`):
   - сборка React-приложения;
   - подготовка статических файлов (legacy + React build);
   - публикация на GitHub Pages.

## Рекомендации

- использовать кеш зависимостей npm;
- разделить CI и deploy, чтобы deploy не обходил quality gate;
- защитить ветку `main` через обязательный статус `CI`.

## Критерий готовности

Ни один merge в `main` не проходит без зеленого CI.

## 2. Quality gate: `lint`, `format`, `typecheck`, тесты

## Цель

Обеспечить стабильное качество кода и предсказуемость релизов.

## Что добавить

В `apps/web`:

- ESLint (TypeScript + React);
- Prettier + проверка форматирования;
- отдельный `typecheck` (`tsc --noEmit`);
- тестовый раннер (Vitest) для unit-тестов;
- React Testing Library для UI/хуков;
- coverage для критичных слоев.

## Рекомендуемые скрипты

- `lint`
- `lint:fix`
- `format`
- `format:check`
- `typecheck`
- `test`
- `test:coverage`
- `check` (агрегированный запуск quality gate локально)

## Приоритет тестирования

1. Репозитории данных и мапперы DTO.
2. Ключевые hooks (`useCompendiumData`, фильтры, модальные переходы).
3. Критичные UI сценарии (поиск, фильтрация, загрузка сущностей, обработка ошибок).

## Критерий готовности

Локально и в CI выполняется:

- `npm run check` в `apps/web`;
- `npm run import:compendium` и `npm run import:news` в `scripts/import-content` (smoke-проверка загрузочного контура).

Если будет добавлен корневой `package.json`, допускается единая агрегирующая команда `check` на уровне корня.

## 3. Процесс `draft -> review -> publish`

## Цель

Управлять качеством и жизненным циклом контента через формальный редакционный процесс.

## Целевая модель

Каждый контентный документ хранит:

- `status`: `draft | review | published | archived`
- `version`
- `authorId`
- `reviewerId`
- `createdAt`, `updatedAt`, `publishedAt`
- `changeSummary`

## Что добавить

- роль пользователя: `author`, `editor`, `admin`;
- отдельный admin-интерфейс для редактирования и публикации;
- серверная проверка перед публикацией (валидация + целостность связей);
- журнал публикаций (`content_publication_log`).

## Правила переходов статусов

- `draft -> review`: автор отправляет на проверку;
- `review -> published`: редактор/админ публикует;
- `published -> archived`: редактор/админ архивирует;
- прямой `draft -> published` разрешен только `admin` (опционально).

## Критерий готовности

Публичный runtime читает только `published`, а действия публикации доступны только ролям редактора/админа.

## 4. Версионирование контента

## Проблема

Сейчас импорт проставляет фиксированное `version: 1`, что не отражает реальных изменений и осложняет инвалидацию кеша.

## Что внедрить

- инкремент версии на каждый измененный документ;
- `contentManifest/production` с версиями по коллекциям;
- `contentRevision` на уровне релиза (единый номер/метка публикации);
- хранение краткого changelog релиза.

## Стратегия версии

- Версия документа: `doc.version` (целое число).
- Версия коллекции: `manifest.collections.<name>.version`.
- Версия релиза: `manifest.release.version` или `manifest.release.tag`.

## Критерий готовности

После публикации фронтенд гарантированно определяет обновление и корректно инвалидирует кеш.

## 5. Наблюдаемость (observability)

## Цель

Сделать систему измеримой: видеть ошибки, задержки, поведение пользователей и стабильность публикаций.

## Что добавить

### Ошибки и логирование

- централизованный сбор фронтенд-ошибок (например, Sentry/Firebase Crashlytics);
- error boundaries в React;
- структурированные server logs для операций публикации.

### Производительность

- метрики загрузки ключевых страниц (`db`, `character-editor`, `profile`);
- время загрузки коллекций Firestore;
- доля попаданий в IndexedDB cache.

### Контентные метрики

- число публикаций за период;
- среднее время от `draft` до `published`;
- количество отклоненных публикаций;
- топ правил валидации, которые чаще всего нарушаются.

## Критерий готовности

Команда видит дашборд ошибок/производительности и может быстро диагностировать деградации.

## 6. Production-ready README с архитектурой и roadmap

## Цель

Сделать один главный документ, который объясняет:

- текущее состояние;
- целевую архитектуру;
- правила запуска/развертывания;
- процесс миграции от legacy к новой платформе.

## Структура README (рекомендуемая)

1. Краткое описание проекта и стек.
2. Архитектурная схема (legacy + React + Firebase + data pipeline).
3. Локальный запуск (web, import scripts, локальные проверки).
4. Quality gate и команды проверки.
5. CI/CD и веточная стратегия.
6. Модель контента и статусы публикации.
7. Политика версионирования и кеш-инвалидации.
8. Наблюдаемость и ключевые метрики.
9. Roadmap миграции (этапы и ожидаемые результаты).
10. Раздел рисков и ограничений.

## Критерий готовности

Новый участник команды может запустить проект, понять архитектуру и процесс релиза без внешних пояснений.

## Приоритет внедрения (порядок работ)

1. Quality gate в `apps/web` + базовые проверки для `scripts/import-content`.
2. CI workflow (блокирует деградацию качества).
3. Deploy workflow (стабильная публикация после зеленого CI).
4. Версионирование контента + корректная инвалидация кеша.
5. Draft-review-publish процесс.
6. Observability.
7. Обновленный README и roadmap (можно вести параллельно, но финализировать после первых 4 пунктов).

## Оценка сроков

Для одного разработчика:

- CI/CD + quality gate: 4-7 рабочих дней;
- versioning + manifest upgrades: 2-4 дня;
- draft/review/publish (MVP): 7-12 дней;
- observability (базовый уровень): 3-6 дней;
- production README + roadmap: 1-2 дня.

Итого базовый контур: 17-31 рабочий день.

## Формулировки для пояснительной записки

1. Реализован контур непрерывной интеграции и доставки, обеспечивающий автоматическую проверку качества и воспроизводимую публикацию системы.
2. В проект внедрен quality gate (статический анализ, проверка форматирования, типизация, тестирование), снижающий вероятность регрессий.
3. Реализован редакционный жизненный цикл контента `draft -> review -> publish` с разграничением прав доступа и аудитом публикаций.
4. Разработана схема версионирования контента, обеспечивающая согласованность клиентского кеша и актуальность данных.
5. Внедрена система наблюдаемости, включающая мониторинг ошибок, производительности и метрик контентного процесса.
6. Подготовлена единая техническая документация уровня production-ready с архитектурной картой и этапами миграции.
