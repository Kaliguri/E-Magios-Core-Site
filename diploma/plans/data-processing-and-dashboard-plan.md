# План внедрения обработки данных и визуального дашборда

## Назначение документа

Документ фиксирует рекомендуемую архитектуру и этапы внедрения модуля обработки данных для проекта E'Magios Core, а также полноценного визуального дашборда для аналитики контента и бросков кубов пользователей.

Цель: получить технически обоснованное решение, которое одновременно:
- усиливает качество данных проекта;
- дает наглядную аналитику для команды и пользователей;
- хорошо описывается в пояснительной записке дипломного проекта.

## Рекомендуемое решение для проекта

Для проекта рекомендуется внедрить единый контур:

1. Нормализация данных (pre-processing).
2. Валидация данных (структура, полнота, корректность).
3. Проверка связей между сущностями (целостность ссылок).
4. Генерация статистического отчета.
5. Полноценный визуальный дашборд (основной интерфейс аналитики).
6. Отдельный контур аналитики бросков кубов (персональной и глобальной).

Приоритет: дашборд не как опция, а как целевой основной слой представления результатов обработки данных.

## Архитектура обработки данных

## 1) Источники данных

- `data/*.json` (справочник: заклинания, школы, эффекты, действия и другие сущности).
- события бросков кубов (клиентские и/или серверные события).
- пользовательские данные (профиль, персонажи, идентификатор пользователя).

## 2) Pipeline скриптов

Рекомендуемый набор:

- `normalize_data.py`
- `validate_data.py`
- `check_relations.py`
- `generate_data_report.py`
- `build_search_index.py` (второй приоритет после базового контура)
- `process_data.py` (единая точка запуска)

Порядок выполнения:

1. Нормализация входных JSON.
2. Валидация схемы и доменных правил.
3. Проверка ссылочной целостности.
4. Подсчет агрегатов и статистики.
5. Формирование отчета для дашборда.

## 3) Выходные артефакты

- `data/processed/*.json`
- `reports/validation_report.json`
- `reports/data_report.json`
- `reports/data_report.html` (дополнительно)
- `data/search_index.json` (после внедрения индексации)

## Валидатор данных: обязательные проверки

Минимальный набор правил:

- дубликаты `id` внутри одной коллекции;
- отсутствие `id`, `name` и иных обязательных полей;
- пустые или слишком короткие описания;
- некорректные типы (строка вместо массива и наоборот);
- недопустимые enum-значения (`actionType`, `source`, `status` и т.д.);
- ссылки на несуществующие сущности (например, школа заклинания не найдена);
- некорректный формат массивов связей;
- нарушения договоренной структуры DTO.

Рекомендуемая градация:

- `error` (блокирует публикацию),
- `warning` (не блокирует, но требует исправления),
- `info` (информационные замечания).

## Проверка связей между объектами

Контур связей должен автоматически проверять:

- `spell.school -> schools.id`;
- `school.relatedSchools -> schools.id`;
- `school.educationalSpells -> spells.id`;
- `effect.actionType -> action_types.name` или `action_types.id` (выбрать единый стандарт);
- другие доменные связи по мере расширения модели.

Также рекомендуется формировать обратные связи для аналитики:

- список заклинаний по школам;
- покрытие школ (сколько школ не имеют связанных заклинаний);
- плотность графа связей (среднее количество ссылок на объект).

## Полноценный визуальный дашборд (рекомендуется как основной формат)

## Цели дашборда

- заменить ручной разбор отчетов удобным интерфейсом;
- отслеживать качество контента в динамике;
- видеть активность игроков по броскам кубов;
- получать метрики для принятия продуктовых решений.

## Разделы дашборда

### A. Quality Dashboard (качество данных)

- общее число объектов по коллекциям;
- количество ошибок/предупреждений по каждой коллекции;
- топ проблемных правил валидации;
- динамика качества по версиям импорта;
- таблица битых ссылок с фильтрами.

### B. Content Dashboard (структура контента)

- распределение заклинаний по школам;
- доля заклинаний с концентрацией;
- доля заклинаний с подзаклинаниями;
- объекты с неполными данными;
- плотность связей между сущностями.

### C. Dice Analytics Dashboard (броски кубов)

- количество бросков в разрезе `d4, d6, d8, d10, d12, d20, d100`;
- среднее значение по каждому типу куба;
- медиана, перцентили `P10/P50/P90`, стандартное отклонение;
- сравнение фактического среднего с теоретическим;
- частота критических исходов (например, `1` и максимум грани);
- распределение результатов по времени (день/неделя/месяц).

### D. User vs Global (персональная и общая аналитика)

- персональный средний результат пользователя по каждому типу куба;
- отклонение персональных метрик от глобальных;
- число бросков пользователя за период;
- активность пользователей (DAU/WAU/MAU по броскам);
- лидерборд по активности (по количеству бросков, не по "удаче", чтобы избежать токсичного рейтинга).

## Событийная модель для бросков кубов

Для корректной аналитики рекомендуется фиксировать каждое событие броска в отдельной коллекции, например `dice_roll_events`.

Минимальный формат события:

```json
{
  "eventId": "uuid",
  "userId": "uid_or_anonymous",
  "characterId": "optional",
  "diceType": "d12",
  "sides": 12,
  "result": 9,
  "modifier": 2,
  "total": 11,
  "context": "combat|skill|magic|other",
  "sessionId": "optional",
  "createdAt": "server_timestamp",
  "appVersion": "web-x.y.z"
}
```

Рекомендации:

- `createdAt` ставить только серверным временем;
- не хранить персональные данные сверх необходимого;
- ввести retention-политику для сырых событий (например, 6-12 месяцев), а агрегаты хранить дольше.

## Агрегации для дашборда

Чтобы дашборд работал быстро, нужны агрегированные коллекции:

- `dice_roll_agg_daily`
- `dice_roll_agg_user_daily`
- `data_quality_agg_by_version`

Источник агрегатов:
- Cloud Functions по расписанию (cron);
- или batch-скрипт в CI/CD после обновления данных.

## Метрики по броскам, обязательные к реализации

- `rolls_count_by_dice_type`;
- `avg_result_by_dice_type`;
- `theoretical_avg_by_dice_type`;
- `avg_delta_from_theoretical`;
- `crit_fail_rate` (результат = 1);
- `crit_success_rate` (результат = максимальная грань);
- `user_avg_vs_global` по каждому кубу;
- `rolls_per_user_per_period`.

## Оценка сложности и сроков

Оценка для одного разработчика при частичной занятости:

### Этап 1: Data Processing Core (1.5-2.5 недели)

- нормализация;
- валидатор;
- проверка связей;
- JSON/HTML отчет.

### Этап 2: Event Tracking для бросков (1-1.5 недели)

- логирование событий броска;
- базовые правила доступа;
- первичные индексы и проверка производительности.

### Этап 3: Агрегации и API для аналитики (1-2 недели)

- дневные/пользовательские агрегаты;
- серверная сверка метрик;
- подготовка данных для графиков.

### Этап 4: Полноценный визуальный дашборд (2-3 недели)

- интерфейс разделов Quality/Content/Dice;
- графики, фильтры, сравнение пользовательских и глобальных метрик;
- экспорт отчетов.

Итого: ориентировочно 5.5-9 недель до зрелой версии.

MVP с рабочим дашбордом и основными метриками: 3.5-5 недель.

## Риски и ограничения

- рост стоимости чтений Firestore при хранении сырых событий без агрегации;
- неконсистентность метрик при отсутствии серверного времени и дедупликации событий;
- перегрузка дашборда нефокусными показателями;
- необходимость четко определить доменные правила до запуска валидатора в блокирующем режиме.

## Критерии готовности (Definition of Done)

- пайплайн `process_data.py` стабильно формирует отчеты без ручных правок;
- критические ошибки валидации блокируют публикацию данных;
- ссылки между сущностями проверяются автоматически;
- дашборд отображает качество данных, структуру контента и метрики бросков;
- доступ к персональной аналитике ограничен владельцем и администраторами;
- для каждого типа куба видны глобальные и персональные средние значения.

## Формулировки для пояснительной записки

1. Реализован модуль нормализации данных, преобразующий неструктурированные источники в унифицированный формат.
2. Реализован модуль валидации структурированных данных, обеспечивающий контроль полноты, корректности и связности объектов предметной области.
3. Реализован модуль обработки связей между сущностями, автоматически проверяющий ссылочную целостность и формирующий карту отношений.
4. Реализован модуль статистической обработки, формирующий агрегированные отчеты по контенту и пользовательской активности.
5. Разработан полноценный визуальный дашборд, отображающий метрики качества данных, структуры контента и аналитики бросков кубов (глобальных и персональных).

## Рекомендуемый следующий шаг

Сначала внедрить этап 1 и 2 (core processing + tracking бросков), затем переходить к этапу 3-4, чтобы дашборд сразу строился на корректных и агрегированных данных.
